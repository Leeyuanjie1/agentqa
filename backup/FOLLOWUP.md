# FOLLOWUP

## 1. 系统负责人补充说明

### 1.1 负责人角色与职责范围
- 对系统整体可用性、稳定性和交付结果负责。
- 负责需求优先级协调、跨模块技术方案把关与关键风险决策。
- 监督关键里程碑执行，确保版本按计划推进并可追踪。

### 1.2 当前阶段重点
- 保证核心流程可闭环运行（解析、检索、生成、校验）。
- 持续跟踪模型与数据资产一致性，避免环境差异导致结果偏移。
- 对高风险事项（性能瓶颈、精度波动、接口兼容）建立预警与处置机制。

### 1.3 风险与边界说明
- 需求边界外的临时新增项，需先评估影响后再纳入周期。
- 外部依赖（模型资源、OCR服务、部署环境）变更时，需同步进行回归验证。
- 未完成验证的优化项默认不进入正式发布路径。

### 1.4 我的判断与取舍补充
- 我的判断优先级是：先稳定、再优化、后扩展。只要核心链路存在不确定性，我会压后体验层和外围能力改造。
- 面对“功能更全”和“交付更稳”的冲突时，我倾向选择可验证、可回滚的最小可行方案，避免一次性堆叠复杂变更。
- 对性能、效果、开发效率三者冲突，我的取舍原则是优先保障线上可用性和结果一致性，其次再做局部提效。
- 对外部依赖相关事项（模型、OCR、运行环境），我会默认按高风险处理，先做兼容与回归策略，再决定是否放量。
- 对无法在当前周期内闭环验证的需求，我的做法是明确标注“暂不承诺上线”，并给出后续评估条件与进入标准。

## 2. 工作方式补充确认

### 2.1 沟通与同步机制
- 日常通过固定渠道同步进展，关键节点以书面形式确认。
- 发生阻塞时，第一时间抛出问题并附带可选方案，不等待被动发现。
- 涉及范围变更、时间调整、质量权衡时，必须显式确认后执行。

### 2.2 任务推进方式
- 采用“需求澄清 -> 方案确认 -> 开发实现 -> 联调验证 -> 发布复盘”闭环。
- 每项任务需有明确负责人、预期输出与完成标准。
- 交付物需满足可复现、可验证、可回溯的基本要求。

### 2.3 质量与验收确认
- 以测试结果和关键指标作为验收依据，不以主观感受替代。
- 对关键改动保留必要的验证记录（测试结论、日志或截图）。
- 验收通过后再进入下一阶段，避免并发推进造成返工。

### 2.4 变更管理约定
- 变更需记录原因、影响范围、回滚方案与执行人。
- 高频变更项优先沉淀规范，减少重复沟通成本。
- 紧急变更执行后需在最近一次同步中补齐说明与复盘。

### 2.5 我的做法补充确认
- 我在接到任务后会先给出书面化结论：目标、边界、风险、时间预估和验收口径，确保各方理解一致。
- 我会将任务拆分为可独立验证的小步提交，每一步都保留可回退点，降低联调和发布风险。
- 对有争议的方案，我会先推进小样本验证或灰度试跑，用结果数据而非观点争论来做决策。
- 我会在每日同步中主动说明“已完成、进行中、阻塞项、需要决策项”，并给出建议选项及影响。
- 我对交付结果负责到底：问题出现后先止损、再定位、再复盘，复盘结论同步沉淀到后续规范中。

### 2.6 本项目工作方式与最小 Demo 思路补充
- 我将 VS Code 作为主工作台，围绕“读代码、改代码、运行验证、记录结论”形成单点闭环，减少工具切换带来的沟通和执行损耗。
- 我提供思路和想法的方式是：先给最小闭环方案，再给可选增强项，确保团队先跑通、再做深。
- 知识库设计上，我主张先简化形态：以结构化文本块和元数据为核心，不在首期引入复杂知识图谱或重型治理流程。
- 检索路径采用“嵌入编码 + 相似度召回”：先用嵌入模型对文档分块编码，检索时按 query 向量召回最相关片段。
- 回答路径采用“召回内容 + LLM 生成”：仅基于已召回证据组织答案，减少模型无依据扩写。
- 对 query 做适量改写：围绕同义扩展、关键实体补全、口语转检索语句三类轻量改写，提升召回率但避免语义漂移。
- Demo 阶段的取舍是“最小可用优先”：先实现导入、编码、检索、回答、基本评估五步闭环，再逐步补充重排、路由和自检。
- 该思路的成功标准是：可以稳定回答一组核心问题，且回答可追溯到知识片段来源。

## 3. 后续推进、验证和交付（含时间表与负责人）

### 3.1 推进时间表与负责人

| 时间 | 阶段目标 | 关键任务 | 负责人 | 交付物 |
| --- | --- | --- | --- | --- |
| 第 1 周 | 跑通最小闭环 | 文档导入、分块、嵌入编码、向量检索、基础问答接口 | AI团队 | 可运行最小 Demo、基础配置文件 |
| 第 2 周 | 提升检索与回答质量 | query 轻量改写、TopK 与阈值调参、引用片段约束回答 | AI团队 | 调参记录、效果对比报告（v1） |
| 第 3 周 | 完成本地化与安全加固 | OCR 本地部署、LLM 本地部署、日志脱敏与权限收敛 | AI团队 | 本地部署说明、数据安全检查清单 |
| 第 4 周 | 验证与试运行 | 真实问题集回归、灰度试运行、问题修复与发布评审 | AI团队 | 验收报告、发布建议、复盘文档 |

说明：
- AI团队对阶段结果和节奏负最终责任，并按模块对质量与交付时效负责。
- 若出现高优先级阻塞，按“当天识别、当天升级、次日给出修复计划”处理。

### 3.2 技术路线确认（安全与能力边界）
- OCR 和 LLM 后续优先采用本地部署方案，默认不将原始业务数据发送到外部云端服务。
- 若因算力或兼容性必须临时使用外部能力，需满足三项前置条件：数据脱敏、审批留痕、可回切本地方案。
- 知识库以向量知识库为主路线，覆盖首期检索与问答闭环，保证实现简单、迭代快。
- 在出现复杂关系推理、多跳检索、实体关系追踪等场景时，再按需引入 KG 增强，不在首期强绑定。
- KG 引入原则：小范围试点、与向量检索并行验证、指标收益明确后再扩大。

### 3.3 验证计划与验收门禁
- 构建固定评测集：高频问题、边界问题、歧义问题、不可回答问题四类样本。
- 关键指标包括：召回命中率、回答准确率、响应时延、不可回答识别率、答案可追溯率。
- 验证方式采用“自动评测 + 人工抽检 + 场景回放”三段式，确保既有指标趋势也有业务可解释性。
- 每周发布候选版本前必须通过门禁：
	- 核心指标不低于上一稳定版本。
	- 关键链路无阻塞级缺陷。
	- 本地 OCR/LLM 部署脚本在目标环境可复现。
	- 关键问题均可追溯到召回片段或规则依据。

### 3.4 交付方案与版本管理
- 交付包内容：可运行代码、部署脚本、配置模板、样例数据、操作手册、常见故障手册。
- 交付文档需明确：系统边界、已验证能力、已知限制、风险项、回滚路径、后续演进路线。
- 版本采用“周迭代 + 月复盘”机制：每周小版本验证交付，每月统一复盘并重排优先级。
- 正式交付条件：目标环境可独立部署、核心指标达标、关键场景通过、回滚方案可执行。
